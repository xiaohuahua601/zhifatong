## 二、两阶段检索架构说明（V6.0 核心）

### 2.1 架构总览

```
用户提问
  │
  ▼
┌─────────────────────────────────────────────────┐
│ 第一阶段：粗排（ANN召回）                        │
│ • Embedding模型: bge-large-zh-v1.5 (1024维)     │
│ • 稠密检索: ChromaDB HNSW                       │
│ • 稀疏检索: BM25（jieba分词）                    │
│ • 融合策略: RRF（倒数排名融合，K=60）            │
│ • 召回数量: 20个候选分块                         │
├─────────────────────────────────────────────────┤
│ 第二阶段：精排（Cross-Encoder）                  │
│ • 服务地址: http://host.docker.internal:9999    │
│ • 模型: BAAI/bge-reranker-v2-m3                 │
│ • 批量打分: 1次HTTP请求完成全部候选              │
│ • 输出数量: Top-5 精排结果                       │
├─────────────────────────────────────────────────┤
│ 生成阶段                                         │
│ • LLM: qwen2.5:1.5b（Ollama本地推理）           │
│ • 上下文: 精排Top-5 + 对话历史（最近10轮）       │
│ • 输出: 回答 + 引用来源 + 置信度                │
└─────────────────────────────────────────────────┘
```

### 2.2 核心配置项（backend/app/config.py）

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `OLLAMA_EMBEDDING_MODEL` | `quentinz/bge-large-zh-v1.5:latest` | 粗排嵌入模型 |
| `RERANK_SERVICE_URL` | `http://host.docker.internal:9999` | 精排服务地址 |
| `RERANK_TIMEOUT` | `30` | 精排请求超时（秒） |
| `CHROMA_EMBEDDING_DIM` | `1024` | 向量维度（bge-large-zh-v1.5） |
| `RAG_RECALL_TOP_K` | `20` | 粗排召回候选数 |
| `RAG_RRF_K` | `60` | RRF融合常数 |
| `RAG_TOP_K` | `5` | 最终返回分块数 |
| `RAG_RERANK_TOP_N` | `5` | 精排输出数量 |

### 2.3 降级容错机制

| 组件 | 主方案 | 降级方案 | 触发条件 |
|------|--------|----------|----------|
| Embedding | Ollama bge-large-zh-v1.5 | 本地哈希向量（jieba+MD5） | Ollama不可用 |
| Reranker | my-rerank Cross-Encoder | LLM逐条打分（qwen2.5） | 精排服务不可用 |

> 降级仅影响检索精度，不中断业务流程。生产环境建议保障两个服务可用。

### 3.3 端口规划（V6.0 当前生效值）

| 服务 | 容器内部端口 | 主机映射端口 | 说明 |
|------|-------------|-------------|------|
| MySQL | 3306 | 13306 | 避免与本地MySQL冲突 |
| Redis | 6379 | 26379 | 避免本地/Hyper-V保留端口冲突 |
| Backend | 8000 | 28000 | 避开8000端口保留区 |
| Frontend | 80 | 8188 | 避免与其他Web服务冲突 |
| Rerank（外部） | 9999 | 9999 | my-rerank容器，项目外独立运行 |
| Ollama（外部） | 11434 | 11434 | 宿主机Ollama服务 |

> **重要**: `.env` 中的端口必须与实际部署一致。历史教训：`.env` 中残留 `REDIS_PORT=6379` 会覆盖 docker-compose.yml 默认值导致端口冲突。

## 五、性能优化配置

### 5.1 后端性能优化（V6.0 当前配置）

| 优化项 | 数值 | 说明 |
|--------|------|------|
| uvicorn workers | 4 | 平衡并发建表冲突与CPU利用率 |
| DB连接池 | 20/worker + 30溢出 | 支持高并发 |
| MySQL max_connections | 1000 | 支持连接池总量 |

> **注意**: workers=4 是经实测校准的值。workers=12 会导致 MySQL 并发建表冲突（错误1050/1684），引发 roles 等表创建失败。

## 六、故障排查指南

### 6.1 容器启动失败

```bash
# 查看容器日志
docker-compose logs backend
docker-compose logs frontend
docker-compose logs mysql

# 常见原因:
# 1. 端口被占用 → netstat -ano | findstr :28000，修改 .env 端口
# 2. Hyper-V端口保留 → 避开8000等保留区，使用28000
# 3. 数据卷残留 → docker-compose down -v 清除卷后重建
```

### 6.2 后端无法连接MySQL

```bash
# 检查MySQL容器状态
docker exec zhifatong-mysql mysqladmin ping -h localhost -u root -pzhifatong_root_2026

# 检查后端日志
docker logs zhifatong-backend 2>&1 | findstr /i "database mysql connect"

# 常见原因:
# 1. MySQL未就绪 → 后端depends_on会等待healthy
# 2. 密码不匹配 → 检查docker-compose.yml中的MYSQL_ROOT_PASSWORD
# 3. 并发建表冲突 → 确认workers=4，后端有建表重试机制
```

### 6.3 前端无法访问后端API（307重定向异常）

```bash
# 检查Nginx代理配置（Host头必须用 $http_host 保留端口）
docker exec zhifatong-frontend grep "proxy_set_header Host" /etc/nginx/conf.d/default.conf
# 正确: proxy_set_header Host $http_host;
# 错误: proxy_set_header Host $host;  ← 会丢失端口导致307重定向Location错误

# 检查后端可达性
docker exec zhifatong-frontend wget -qO- http://backend:8000/health
```

### 6.4 RAG问答无响应或降级

```bash
# 1. 检查Ollama LLM服务
curl http://localhost:11434/api/tags
docker exec zhifatong-backend curl -s http://host.docker.internal:11434/api/tags

# 2. 检查Rerank精排服务（V6.0核心依赖）
curl -X POST http://localhost:9999/rerank -H "Content-Type: application/json" -d '{"query":"测试","documents":["文本"],"top_n":1}'

# 3. 检查Embedding模型
ollama run quentinz/bge-large-zh-v1.5:latest "测试"

# 4. 查看后端降级日志
docker logs zhifatong-backend 2>&1 | findstr /i "rerank embedding 降级 fallback"

# 常见原因:
# 1. Ollama未启动 → 启动Ollama服务
# 2. my-rerank容器停止 → docker start my-rerank
# 3. 嵌入模型未下载 → ollama pull quentinz/bge-large-zh-v1.5:latest
# 4. host.docker.internal不可达 → Docker Desktop设置启用
# 注: 服务不可用时自动降级（哈希向量/LLM打分），检索精度下降但业务不中断
```

### 6.5 ChromaDB向量维度不匹配

```bash
# 现象: 切换嵌入模型后日志报维度不匹配
# 机制: 系统自动检测并删除旧索引重建（无需手动干预）
docker logs zhifatong-backend 2>&1 | findstr /i "维度 vector dim 重建"

# 如需强制重建索引:
docker-compose restart backend
# 启动时若集合为空会自动从MySQL重建（约7个分块）
```

### 6.6 咨询次数429（测试场景）

```bash
# Quota存储在Redis（key格式: quota:{user_id}:{resource_type}:{date}）
# 测试套件会自动重置；手动重置方法:
docker exec zhifatong-redis redis-cli KEYS "quota:*"
docker exec zhifatong-redis redis-cli DEL "quota:3:qa:2026-08-22"

# 注: admin/lawyer账号不受额度限制
```

### 6.7 数据库密码不一致

```bash

# 注意: -v 会删除所有数据卷（含数据库数据），仅首次部署或密码变更时使用
```

## 九、安全注意事项

1. **密码安全**: 生产环境务必修改默认密码（`MYSQL_ROOT_PASSWORD`、`JWT_SECRET_KEY`）
2. **JWT密钥**: 修改 `ZHIFATONG_JWT_SECRET_KEY` 为随机长字符串
3. **HTTPS**: 生产环境需配置SSL证书，通过Nginx反向代理启用HTTPS
4. **防火墙**: 仅开放必要端口（8188/28000），数据库端口（13306/26379）不应对外暴露
5. **IP白名单**: 使用 `ops_automation.py whitelist` 管理授权IP
6. **大模型**: 仅使用本地Ollama模型，严禁调用外部API
7. **XSS防护**: AI回答经后端净化 + 前端DOMPurify双重防护
8. **路径遍历**: 上传接口校验文件名，拦截 `../`、`/`、`\` 等字符
9. **日志**: 定期清理日志，避免敏感信息长期留存
10. **依赖更新**: 定期更新Python和Node.js依赖，修复安全漏洞

### 10.2 两阶段检索数据流

```
MySQL(法律文档) ──启动时索引──→ ChromaDB(1024维向量)
                                      │
用户提问 ──embed──→ 查询向量 ──HNSW──→ 稠密候选 ─┐
用户提问 ──jieba──→ BM25检索 ────────→ 稀疏候选 ─┤→ RRF融合(Top-20)
                                                 │
                    my-rerank Cross-Encoder ←────┘
                              │
                        精排Top-5 ──→ qwen2.5:1.5b ──→ 回答+引用+置信度
```

### 10.3 容器资源限制建议

| 容器 | CPU限制 | 内存限制 | 说明 |
|------|---------|---------|------|
| mysql | 2核 | 1GB | InnoDB缓冲池512M |

| backend | 4核 | 2GB | 4 workers × ~200MB |
